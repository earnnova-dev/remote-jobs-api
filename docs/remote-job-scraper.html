Remote job data: build a scraper, or call an API?

You need structured remote-job listings from several boards. The honest trade-off is between maintaining your own per-board scrapers and consuming one normalized data endpoint. Here's what each actually costs you, with runnable Python.

🟢 live today 5 boards JSON + CSV 0-100 fit score

The problem with scraping remote job boards

Every board does it differently. Remotive is JSON but paginates in a particular way; RemoteOK and We Work Remotely are HTML you have to parse; Jobicy and Hacker News (Who Is Hiring) have their own shapes. If you build the scraper yourself you own all of it:

  • Per-board format drift. Boards change class names and response fields with no notice. One bad deploy upstream and your pipeline silently returns garbage or an empty list.
  • Duplicate listings. The same role appears on multiple boards. Without dedup you double-count every "opportunity" you report.
  • Rate limits and breakage. Each endpoint has its own tolerance. Scraping five boards concurrently means five ways to get blocked or throttled.

None of that is interesting business logic. It's maintenance you're paying for on a recurring basis.

Option A — build your own scraper

Start with a per-board fetch and parse. For a JSON board it looks roughly like this:

import requests, json

def remotive(limit=20):
    r = requests.get("https://remotive.com/api/remote-jobs",
                     params={"limit": limit}, timeout=20)
    r.raise_for_status()
    return r.json()["jobs"]

jobs = remotive()
print(len(jobs), "jobs")
print(jobs[0]["title"], "|", jobs[0]["company_name"])

That works — until the response changes. Then you repeat the whole exercise for RemoteOK (HTML → you need a parser), We Work Remotely (HTML, category-scoped), Jobicy, and the Hacker News "Who Is Hiring" thread (an Algolia search on a monthly post). Five adapters, five maintenance loops, five different ways to break. And every downstream consumer has to re-normalize each board's fields by hand.

Cost: high upfront, and a permanent recurring tax the moment you add boards or a board changes.

Option B — call a normalized data API

Push the scraping and normalization to one place and consume the result. Remote Jobs API pulls the five boards (Remotive, RemoteOK, Jobicy, We Work Remotely, Hacker News), normalizes each listing into a single schema, dedupes, and returns JSON or CSV — plus an optional deterministic 0–100 skill fit-score for ranking. You get one call:

pip install remote-jobs-api

# query the feed directly, rank by skill, cap the list
remote-jobs-api --skills python,api --limit 3

# or run it as a REST server
remote-jobs-api --serve --port 8000

From Python it's the same endpoint shape:

import json, subprocess

out = subprocess.check_output(
    ["remote-jobs-api", "--skills", "python,api",
     "--limit", "50", "--format", "json"])
data = json.loads(out)          # {"count": N, "query": {...}, "jobs": [...]}
for j in data["jobs"][:5]:
    print(j["title"], "|", j["source"], "| fit", j["fit_score"])

Each job is already normalized — title, company, location, salary, tags, source, fit_score — so a remotive row and a wwr row are interchangeable. No per-board adapters on your side, no session scraping, no browser. It's pure Python stdlib, so it runs on a laptop, a $5 VPS, or the included Dockerfile.

Cost: low. You trade "own every board's internals" for "consume one schema" — and you stop re-parsing when a board changes.

Rule of thumb: if you need one board you deeply control, scrape it. If you need several boards as one clean dataset and don't want to own the breakage, use the API.

Bottom line

Scraping is a means to an end you rarely actually want — you want the data. If the end is "structured remote jobs from multiple boards," the cheapest durable path is to consume a normalized feed rather than maintain five fragile scrapers. Remote Jobs API is self-hostable and stdlib-only, so there's no lock-in: point it at your stack, or read the source and fork it.
